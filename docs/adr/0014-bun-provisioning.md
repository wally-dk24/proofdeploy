# ADR-0014: Bun as a Node Package Manager (Plan 1.2e, D22)

**Date:** 2026-10-15
**Status:** Accepted

## Context

Node repos whose root lockfile is `bun.lock` were unprovisionable:
the plan selected bun, but the sandbox executor refused it ("not
yet supported in the sandbox"), and bun is not present on the
pinned Node images nor distributed by corepack (the mechanism the
other pinned managers use). In the 2026-10-14 ten-repo readiness
re-run that refusal blocked three hono sides outright, and it
gated Vendure (a bun monorepo) behind plan 1.2b's workspace
support. Master's decision D22 adds bun as a Node package
manager: frozen installs from `bun.lock`, bun itself pinned by
digest with the version aligned to the app, and bun workspaces
through plan 1.2b's existing `plan_workspace`.

## Decision

1. **Manager selection is unchanged in shape.** `bun.lock` at the
   root selects bun (via `select_package_manager`, as before);
   the install is `bun install --frozen-lockfile`. A
   lockfile/manifest mismatch is the frozen install's own failure
   (bun: "lockfile had changes, but lockfile is frozen") →
   BUILD_FAILED — never a silent fallback to another manager and
   never a generated lockfile.
2. **`bun.lockb` is a typed refusal.** The legacy binary format
   is opaque and version-stamped by the bun that wrote it;
   equivalence with the text `bun.lock` cannot be proven from
   the plan's side, so a snapshot whose selected lockfile is
   `bun.lockb` refuses typed, naming the conversion path.
3. **Bun is pinned by digest, in a committed table.**
   `BUN_RELEASE_SHA256` in `proofdeploy/provisioning.py` maps a
   bun version and machine architecture to the sha256 of the
   official release zip (`bun-linux-x64.zip` /
   `bun-linux-aarch64.zip` from oven-sh/bun GitHub releases),
   resolved from each release's own `SHASUMS256.txt` and verified
   against the downloaded artifacts — the same committed-pin
   discipline as `images.lock.json` and the Python managers'
   hash-pinned bootstrap requirements files. A bun version with
   no row in the table is a typed refusal: there is no unpinned
   bun install.
4. **The version aligns to the app** (the generic-alignment
   principle): the app's own `packageManager: bun@<version>`
   when declared, else the table's default version. The
   selected version and the artifact digest are recorded on the
   plan (`bun_version` / `bun_sha256`), so the record always
   names the exact bun that ran the frozen install.
5. **Provisioning is a persisted bootstrap step.** Bun is not
   corepack-distributed and corepack cannot pin it, so the plan
   carries one `bash -c` bootstrap step (the shape of the Python
   adapters' `-c` code steps): download the pinned release zip
   into the checkout's `.pd-tools`, verify its sha256
   (`sha256sum -c`), unpack, and install the binary at
   `{checkout}/.pd-tools/bin/bun` — the Addendum 35
   persisted-tools pattern (each sandbox step is its own `--rm`
   container; only the checkout survives). The frozen install
   then runs through that binary. Non-interactive throughout
   (`curl -f`, `unzip -o`). The bootstrap's tools (`curl`,
   `unzip`, `sha256sum`) are verified present in the pinned
   Node image (node:22.23.3-bookworm).
6. **Contract steps resolve the plan's bun.** A bun app's own
   contract steps may call `bun` (its build/start — Vendure's do),
   so both executors put the bootstrapped `.pd-tools/bin` first
   on PATH for a bun plan's contract steps: the sandbox renders
   it into the step command (alongside `node_modules/.bin`), the
   host executor prepends it to the step PATH. This is plan data
   driving rendering, exactly like the `node_modules/.bin`
   treatment.
7. **Workspaces:** bun joins the supported-manager set inside
   the existing `plan_workspace` (pnpm, npm, bun) with no
   interface or contract change; bun workspaces scope by the
   resolved `app.path` exactly like the others. Yarn workspaces
   remain a typed refusal naming the manager.

## Evidence

- The golden `conformance/golden/node-bun-sqlite` (the
  node-pnpm-sqlite app shape under bun, `bun.lock` generated by
  the digest-verified bun 1.4.3) passes the kit's ten
  conformance cases in CI alongside the other goldens.
- The pin table's 1.4.3 x86_64 digest was verified end-to-end
  during development: the release zip downloaded from GitHub
  hashes to the table value.
- Plants (mutated lockfile, dropped `--frozen-lockfile`,
  unpinned bun version) are recorded in the PR for this ADR's
  plan line: each fails typed/frozen, never silently.
