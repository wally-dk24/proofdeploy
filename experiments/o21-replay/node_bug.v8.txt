# ProofDeploy blind probe authoring

You are writing black-box HTTP probes for a code change. You are shown: the fixture (a description of the running instance and its data), the diff, the repository's file list, the full text of the files the diff touches (lines the diff adds or changes are marked `<<CHANGED>>` at the start), the route declarations of the app, and an authoring skill section (which may be empty).

The change may be correct or it may contain a bug. Your probes decide which: every expected value must come from evidence outside the changed lines, quoted in the assertion's `evidence`. A probe should pass on an app that behaves as the evidence says and fail on one that does not, whatever the diff does.

## Output format

Write any reasoning first, in plain prose. Then output each probe as its own fenced ```json block. Blocks contain JSON only: no comments, no `...`, no text outside the JSON.

This complete example shows every allowed form. Copy its shapes exactly:

```json
{
  "setup": [
    {"type": "http",
     "act": {"method": "POST", "path": "/items", "headers": {"Authorization": "Bearer ${AUTH_TOKEN}"}, "body": {"name": "probe item"}},
     "capture": {"ITEM_ID": {"from": "body", "json_path": "id"}}}
  ],
  "act": {"method": "GET", "path": "/items/${ITEM_ID}", "headers": {"Authorization": "Bearer ${AUTH_TOKEN}"}},
  "assert": [
    {"type": "status", "equals": 200, "evidence": {"source": "fixture", "quote": "<exact text from the fixture>"}},
    {"type": "body", "json_path": {"path": "name", "equals": "probe item"}, "evidence": {"source": "src/items.js", "quote": "<exact text from that file>"}},
    {"type": "body", "contains": "probe item", "evidence": {"source": "src/items.js", "quote": "<exact text>"}},
    {"type": "body", "matches": "^\\{", "evidence": {"source": "src/items.js", "quote": "<exact text>"}},
    {"type": "header", "name": "Content-Type", "contains": "json", "evidence": {"source": "src/items.js", "quote": "<exact text>"}},
    {"type": "db", "query": "SELECT id FROM items WHERE name = 'probe item'", "count": 1, "evidence": {"source": "src/items.js", "quote": "<exact text>"}}
  ]
}
```

Rules for each part:
- `act`: `method` and `path` are required; `method` is one of GET, HEAD, POST, PUT, PATCH, DELETE. `headers` (an object) and `body` (any JSON value) are optional.
- `setup`: a list of steps, possibly empty. Each step has `"type": "http"`, an `act` as above, and optionally `capture`. A `capture` maps a NAME to exactly `{"from": "body", "json_path": "<dotted path>"}`. Omit `capture` if you capture nothing; never write an empty one.
- Two different `json_path` shapes exist on purpose: inside `capture` it is a string (`"json_path": "id"`); inside an assertion it is an object (`"json_path": {"path": "id", "equals": 1}`).
- `assert`: a non-empty list. Every assertion has a `type` (status, body, header or db) and a top-level `evidence` object. `evidence` is never placed inside `json_path`.
- `status` `equals` and `db` `count` are integers. `db` queries are read-only SELECT statements.
- Placeholders such as `${AUTH_TOKEN}` and `${NAME}` appear only inside JSON strings. `${AUTH_TOKEN}` is the token the fixture describes; `${NAME}` is a value you captured earlier.
- Credentials: you may use credentials the fixture states, and you may create new users in setup with credentials you choose. Never invent credentials for other existing accounts, and never write a literal token you were not given.
- For a library (the fixture says so), a setup step may be `{"type": "harness_app", "language": "python" or "node", "source": "<a minimal app that mounts the library and serves HTTP>", "entrypoint": "<the source's file name, e.g. app.py or app.js>"}`. Its base URL replaces the target URL.

Rules for `evidence`:
- `source` is a file path shown in this prompt, or the literal string `"fixture"`. Only text shown in this prompt can be quoted; a file that is listed but not shown cannot.
- `quote` is copied exactly from that source (at most 300 characters). It must not be a line marked `<<CHANGED>>`, or any line the diff adds or changes, including changed tests.
- The quote must contain the expected value's text: the number for `status`, `count` and numeric `equals`; `true` or `false` for a boolean (any capitalisation); the string itself for `contains` and string `equals`; for `matches`, a string the pattern matches. For a true/false value, quote only the part about this record: a quote containing both `true` and `false` is refused.
- If no shown text outside the changed lines supports a value, do not assert that value.

The harness checks every assertion against these rules before anything runs. Errors are sent back to you once to fix; anything still wrong is dropped and counts against you.

Caps: full text is shown for at most 20 touched files, at most 100000 bytes per file; at most 200 files are listed; route declarations up to 32 KB.

## Authoring skill

# Probe-Authoring Skill

**How to use this document:** Read all of it before opening the author bundle. It teaches how to decide what is correct and how to probe for it, not what bug to find.

---

## 0. The rule that decides every expected value

R1. The change you are reviewing is a claim, not a fact. It may be the bug. Never use the changed lines as evidence that the new behavior is correct.

R2. Every expected value you assert, including status codes, must come from evidence outside the changed lines: the fixture's description of the instance and its data, unchanged tests, docs, comments, field and function names, or code the change did not touch. Tests the change adds or edits are part of the claim, not evidence.

R3. Quote that evidence word for word in the assertion's `evidence` field. The harness checks every quote before anything runs: it must exist in the bundle, it must not come from a changed line (marked `<<CHANGED>>`), and it must contain the value you expect. An assertion that fails this check is sent back to you once to fix; if it is still wrong, it is dropped and counts against you.

R4. If nothing outside the changed lines tells you what a value should be, do not assert that value. Probe other behavior around it that the evidence does settle.

---

## 1. Procedure, in this order

1. **Facts first.** Before reading the diff, read the fixture and the unchanged code, tests and docs near the touched files. In your prose reasoning (before the JSON blocks), write down each fact you will rely on, with its exact quote and where it is. For example: *the fixture says "account 7 has balance 250"*.

2. **Then the change.** Read the diff. List each behavior it changes or adds, one per line, in your own words.

3. **Compare.** For each listed behavior, check it against your facts. If the change agrees with them, your probes expect that behavior. If the change contradicts them, your probes expect what the facts say, and they should fail against this change. If no fact covers it, apply R4.

4. **Who and how.** For each behavior, ask which actors can reach it (an authenticated user, an unauthenticated request, a scheduled job, another service), in which states (an existing record, a flag set, a prior request completed) and with which inputs. Trace each untrusted input from the boundary (path, query, header, body) to where it is used, and note where it is validated, normalized, escaped or passed through unchanged.

5. **Probe both sides.** When the change adds a guard, check or validation, probe an input that should pass it, an input that should be rejected, and the boundary between them.

6. **Shape.** Every probe is setup / act / assert. Setup creates the preconditions; act performs one operation; assert checks only what is observable from outside: status codes, headers, response bodies, read-only database state. Never assert on internals (variables, call counts, log lines).

7. **Pairs.** For each behavior, write at least two probes: the normal case and an adversarial case from section 2. A useful probe gives different results for the old and the new behavior; which result counts as a pass is decided only by the evidence, never by the diff. Each probe must exercise changed behavior, possibly reached through a route the change did not touch (item 13).

---

## 2. Adversarial questions

Ask these about every behavior the change touches. The answers come from the bundle, not from this list.

8. For batch operations, what happens when one record in the batch carries a hostile value?

9. What happens with no authentication at all, or as a different user?

10. What happens with an empty, missing or malformed input where the code expects a well-formed one? Does it reach the same handler, a different handler or an error path?

11. When the change introduces two or more conditions, what happens when more than one applies, or when they disagree? Probe the combinations, not just each condition alone.

12. What happens when the same logical input is written differently (case, encoding, whitespace) or arrives as an unexpected type (a dict where a string was expected, bytes where text was expected, a list where a scalar was expected)?

13. Can the same request reach a route or handler the change did not touch? If so, probe that path too.

---

## 3. Worked examples

Study the pattern, not the specific bug. The first example is about deciding the expected value; the others are real bug fixes, cited by commit SHA.

14. **Expect what the evidence says, not what the change does.** Suppose the fixture says *"account 7 has balance 250"*, and the change edits how balances are read, introducing a bug. Expect balance 250 for account 7, with evidence `"account 7 has balance 250"` (source: fixture). Do not expect whatever number the new code would compute. If the new code returns something else, your probe fails, which is exactly the point.

15. **Probe every input position in a batch.** In CodeIgniter4 `f5e463b9a3e986389ce285963e51a7f1fab6559f` (fix for deleteBatch() SQL injection), `deleteBatch()` with `where()` conditions substituted bind values raw into the DELETE SQL, ignoring the escape flag; the fix routes them through `convertWhereBindsForBatch()`, which respects escaping. A probe that calls the batch operation with `where()` values containing SQL metacharacters, and checks whether they are treated as values or as code, would have caught it. Whenever a change assembles a query or command from per-record inputs, probe each input position with a hostile value.

16. **Vary the representation.** In Fastify `179619c8e99d54924309b9933402151ef9af37e0` (fix for header schema bypass), mixed-case header names slipped past validation; the fix normalized names before checking. A probe that sends the same header as `Content-Type`, `content-type` and `CONTENT-TYPE` and checks that validation treats them alike would have caught it.

17. **Send the unexpected type.** In Django `ebcb13b327301f28cbc6cd5e4988a719f00575aa` (fix for GIS spatial lookup file write), dict and bytes values in spatial lookups reached code that treated them as file paths; the fix rejected unsafe types. A probe that submits a dict or bytes where the API documents a string would have caught it.

---

## 4. Format (an invalid probe is never sent and counts against you)

18. Follow the output format at the top of this prompt exactly, copying the shapes in its complete example. The two most common slips: `evidence` goes at the top level of the assertion, never inside `json_path`; and `capture` is either omitted or maps a NAME to `{"from": "body", "json_path": "<dotted path>"}`, never an empty object.

19. Quote only text shown in this prompt. For a true/false value, quote only the part about the record you are checking, not a sentence that contains both values.

---

## 5. Final check before you answer

20. For every assertion, status included: Is the expected value backed by a quote from outside the changed lines? Is the quote copied exactly? Does it contain the value, and only the value for this record? If not, fix it or remove the assertion (R4).

21. For every probe: Does it match the format in section 4? Would it fail if the behavior it checks were wrong?

22. Do not write only happy-path probes, and do not stop at the first probe that passes. Cover section 2 for each behavior you listed in step 2.
